\section*{The short answer}

SLM360 is an on-device language engine made by 360 Labs (Lightyear 360 Labs Pvt Ltd, India). Its main job is to read
a short command and pick one action from a fixed list. Kestrel is an offline personal assistant. It also picks
actions, but it can write emails, translate, rewrite text, answer questions from your notes and write small programs.

\begin{itemize}
  \item \textbf{SLM360 is far ahead on size and on phones.} Its intent model is about 33 times smaller than Kestrel's
  (4\,MB vs 132\,MB), and its text model about 45 times smaller (63\,MB vs 2.84\,GB). 360 Labs describes Android apps
  built on it. Kestrel has never run on a phone.
  \item \textbf{Kestrel is ahead on accuracy, languages, abilities and proof.} On the same 150-intent test
  (CLINC150), Kestrel's intent step scored 95.9\% on 4,500 test sentences; SLM360 Nano's page claims 85.1\%. SLM360's
  headline 98--100\% comes from tests of only 49 and 50 sentences. Kestrel measured Hinglish; SLM360's paper is
  English only.
  \item \textbf{Many SLM360 numbers cannot be checked.} The model is not public, no test phone is named, the paper's
  ``raw results'' link returns an error (404), and the same model is described with three different sizes.
\end{itemize}

\noindent In one sentence: \textbf{SLM360 is small enough for phones but proves little; Kestrel proves what it does
but is too big for phones.}

\section{How this comparison was made}

\begin{itemize}
  \item \textbf{Kestrel:} numbers from the committed logs in this repository, all measured on one laptop: AMD Ryzen 5
  5500U, 6 cores, 14\,GiB RAM, Fedora 44, CPU only, no GPU. Appendix A lists the file behind each number.
  \item \textbf{SLM360:} six public pages on 360labs.ai, read on 28 October 2026 (Appendix A). These are the company's
  own claims. The model is \quoted{available for licensing} and is not public, so we could not run it on the same
  data or the same hardware.
  \item When two numbers come from different hardware or different tests, the text says so. Sizes are in decimal
  megabytes (1\,MB = 1,000,000 bytes) unless MiB is written.
\end{itemize}

\noindent\textbf{What this means.} On everything that decides whether an assistant fits on a phone (file size, memory,
phone builds), SLM360 is ahead by 6 to 45 times, and more against the KAVACH model. This gap is real, and it is the
main thing Kestrel would have to fix to reach phones.

\subsection*{SLM360 contradicts itself}

\begin{itemize}
  \item \textbf{Three sizes for one model:} 577K parameters and 848\,KB (KAVACH paper); 6.4M parameters and 4\,MB (Nano
  page); a 32\,MB model and 50\,MB in total (SLM360 paper).
  \item \textbf{``Pure Rust with zero external ML dependencies''}, but the same page lists an \quoted{ONNX model
  (32MB)}, and the KAVACH app, which uses SLM360, names \quoted{TensorFlow Lite 2.14.0} as its ML runtime.
  \item \textbf{``Proprietary'' model:} the paper calls it proprietary, but its own benchmark commands load
  \texttt{gte-small-quantized.onnx}, a public embedding model.
  \item \textbf{Phones:} one section of the model page says \quoted{iOS and Android planned}; another lists
  \quoted{Android via JNI bindings}.
  \item \textbf{Speed vs Rasa:} \quoted{4x faster} in the abstract, \quoted{3.8x faster} in the results.
\end{itemize}

\section{Not a contest: different jobs}

\begin{itemize}
  \item \textbf{Camera detection} of people and vehicles (YOLOv8n, 12\,MB), \textbf{drone sounds}, \textbf{patrol
  routes} (A* path search) and \textbf{reports} (filled-in templates) are features of 360 Labs' apps, but they are not
  SLM360. VAJRA, the drone app, does not use SLM360 at all. Kestrel does not try to do any of these.
  \item \textbf{Why a 45\,MB app can do so much:} in KAVACH, SLM360 is 0.85\,MB. The rest is a standard 12\,MB
  detector, ordinary code, a map and the screens. Picking one of 25 actions needs only a small model; writing free text
  needs a large one.
  \item \textbf{Fair pairing:} Kestrel's intent step does the same job as SLM360 Nano. Kestrel's Gemma step has no
  real counterpart in SLM360's phone apps.
\end{itemize}

\section{Kestrel's own weak spots}

Kestrel's logs also show where it falls short, regardless of SLM360:

\begin{itemize}
  \item On CLINC150, the encoder alone (89.3\%, 5.6\,ms on average) beat Kestrel's full cascade (87.4\%, 146\,ms on
  average). Sending hard cases to Gemma made results worse there.
  \item On the small English--Hinglish set (252 items), the cascade (96.8\%) stayed below always using Gemma (100\%).
  The result is inconclusive.
  \item The English--Hinglish test sets are small and synthetic (252 and 280 items).
  \item Programs that read input: 3 of 6 right. Translation into Hinglish: 1 of 4 (development data only).
  \item Everything was measured on one laptop.
\end{itemize}

\section{What this means if Kestrel goes to phones}

\begin{itemize}
  \item \textbf{Size is the main problem.} The intent step must shrink from 132\,MB to a few MB. Gemma (2.84\,GB) is
  the bigger question: either it stays on the laptop and the phone sends it only the hard requests, or it is measured on
  a phone with a lot of memory.
  \item \textbf{Going small has a cost.} If SLM360's numbers hold, a 4\,MB model loses about 10 points on CLINC150
  compared with Kestrel's encoder. A smaller Kestrel encoder must be measured, in English and in Hinglish, before it
  replaces the current one.
  \item \textbf{Nothing has been measured on a phone yet.} Every phone statement in this section is a plan, not a
  result.
\end{itemize}
